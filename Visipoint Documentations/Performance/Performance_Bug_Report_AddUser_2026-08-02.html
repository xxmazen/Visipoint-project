Expected: A freshly-obtained access token should remain valid for authenticated calls made immediately after login, regardless of concurrent sessions or system load.

Actual: Add User fails 100% of the time across all three tested ramp-up speeds — including the 5-minute run where Login succeeded 100% of the time with healthy sub-second response times. This rules out load, timing, and connection contention entirely.

Root cause (now confirmed, not just suspected): The backend invalidates a user's previous session token whenever that account logs in again. With 1000 threads logging into the same account — even spaced 300ms apart on average at the 5-minute pace — every earlier thread's token is superseded by a later login before it can be used again. The 5-minute run is the cleanest possible demonstration: the system has zero trouble processing the logins themselves (proven by Login's perfect record), so Add User's 100% failure is entirely attributable to the session/token lifecycle design, not capacity.

Practical implication: this will reproduce with as few as 2 concurrent logins to the same account — no load or scale required. Any real user logged in from two tabs or two devices simultaneously likely has their first session's authenticated actions silently broken the moment the second login completes.

No further investigation needed on Login — not a bug, and it fully recovers with reasonable pacing.

Recommendations

  1. Escalate BUG-PERF-001 / BUG-PERF-003 immediately — now a confirmed, load-independent backend bug, reproduced identically across three test runs and two endpoints (Logout, Add User), including one run where the system was provably healthy in every other respect.
  2. Reproduce with 2 concurrent logins (no load tool needed) to get a minimal repro case for engineering.
  3. Close out the Login performance question — 30s/90s degradation was pacing-related and fully resolves at gentler ramp-up; no further load testing needed there.
  4. Once the session-invalidation bug is fixed, this same test plan (switched back to a fast 30s ramp-up) becomes a good regression/capacity test for Add User's real backend performance, since the token bug currently masks any genuine capacity data for that endpoint.
